# `1`. `MySQL` 支持日志

`MySQL` 有不同类型的日志文件，用来存储不同类型的日志，分为**二进制日志**、**错误日志**、**通用查询日志**和**慢查询日志**，这也是常用的4种。`MySQL 8` 又新增两种支持的日志：**中继日志**和**数据定义语句日志**。使用这些日志文件，可以查看 `MySQL` 内部发生的事情。|

**这6类日志分别为：**

1.  **慢查询日志**：记录执行时间超过 `long_query_time` 的 `SQL`，以及未使用索引的查询（可选）
2.  **通用查询日志**：记录**所有**客户端连接和执行的 `SQL` 语句（包括 `SELECT`）
3.  **错误日志**：记录 `MySQL` 启动、运行、关闭过程中的异常信息，以及严重错误（如崩溃、死锁、权限问题等）
4.  **二进制日志**：记录所有**修改数据或可能修改数据**的语句（`DDL`、`DML`，不包括 `SELECT` 等只读操作），以事件形式存储
5.  **中继日志**：用于主从服务器架构中，**从库（`Slave/Replica`）专用**。从库的 `I/O` 线程把主库 `binlog` 事件写入 `relay log`，`SQL` 线程再读取 `relay log` 重放
6.  **数据定义语句日志**：记录 `DDL` 语句执行的**元数据操作**，保障 `MySQL 8.0` 中**原子 `DDL`** 的实现。`DDL`（如 `CREATE`、`DROP`、`ALTER`）

| 层次                       | 日志类型     | 主要目的             |
| :------------------------- | :----------- | :------------------- |
| **`Server` 层**            | 错误日志     | 故障排查             |
|                            | 二进制日志   | 复制、恢复、审计     |
|                            | 通用查询日志 | 调试                 |
|                            | 慢查询日志   | 性能调优             |
|                            | 中继日志     | 从库复制             |
|                            | `DDL` 日志   | 原子 `DDL`、崩溃恢复 |
| **存储引擎层（`InnoDB`）** | `Redo Log`   | 持久性、崩溃恢复     |
|                            | `Undo Log`   | 原子性、`MVCC`       |



## `1.2` 日志的弊端

-    日志功能会**降低** `MySQL` 数据库的性能。例如，在查询非常频繁的 `MySQL` 数据库系统中，如果开启了通用查询日志和慢查询日志，`MySQL` 数据库会花费很多时间记录日志。
-   日志会**占用大量的磁盘空间**。对于用户量非常大、操作非常频繁的数据库，日志文件需要的存储空间设置比数据库文件需要的存储空间还要大



# `2`. 慢查询日志(`slow query log`)

-   **核心用途**：**性能调优**，定位慢 `SQL`
-   **相关参数**：
    -   `slow_query_log`：开关
    -   `long_query_time`：阈值（秒），默认 10
    -   `log_queries_not_using_indexes`：记录未走索引的查询
    -   `slow_query_log_file`：日志路径
-   **分析工具**：`mysqldumpslow`、`pt-query-digest`

---

1.   查看 开启慢查询日志参数

     ```sql
     # OFF 关闭。ON 打开，默认关闭
     SHOW VARIABLES LIKE 'slow_query_log%';
     
     # slow_query_log_file 是日志存放地址
     ```

2.   开启慢查询日志

     ```sql
     SET GLOBAL slow_query_log = 'ON';               # 生产不要开
     SET GLOBAL slow_query_log = 'OFF';              # 关闭
     ```

3.   查看 慢查询时间 阈值 

     ```sql
     SHOW VARIABLES LIKE 'long_query_time';          # 默认是 10s，执行时间 > 10s 的 SQL 会被记录
     
     SET GLOBAL long_query_time = 2;                 # 设置阈值为 2s，超过2s就记录，生产不要动
     ```

4.   查看慢查询记录数

     ```sql
     SHOW STATUS LIKE 'slow_queries';
     ```

5.   慢查询日志分析工具 `mysqldumpslow`（`Linux` 版本）

     ```sql
     mysqldumpslow -help
     
     mysqldumpslow -s t -t 5 /data/mysql/MySQL-slow.log
     ```



# `3`. 通用查询日志(`general query log`)

-   **作用**：记录**所有**客户端连接和执行的 `SQL` 语句（包括 `SELECT`）。
-   **特点**：信息全但开销大，生产环境一般**不开启**，仅用于调试。
-   **相关参数**：
    -   `general_log`：开关。
    -   `general_log_file`：日志文件路径

---

1.   查看通用查询日志参数

     ```sql
     # general_log 是开关（OFF 关闭，ON 打开），默认关闭
     SHOW VARIABLES LIKE 'general_log%';
     
     # general_log_file 是日志存放地址
     ```

2.   开启/关闭通用查询日志

     ```sql
     SET GLOBAL general_log = 'ON';       # 生产不要开
     SET GLOBAL general_log = 'OFF';      # 关闭
     ```

3.   设置日志输出方式

     ```sql
     SHOW VARIABLES LIKE 'log_output';    # 默认 FILE，可改为 TABLE 或 FILE,TABLE
     SET GLOBAL log_output = 'FILE';
     ```

4.   表方式查看日志（`log_output` 包含 `TABLE` 时）

     `log_output` 是 `FILE` 的话可以去查看日志文件

     ```sql
     # log_output 包含 TABLE 时
     SELECT * FROM mysql.general_log
     ORDER BY event_time DESC
     LIMIT 10;
     ```



# `4`. 错误日志(`error log`)

>   错误日志**默认开启**的，好像还管不了

-   **作用**：记录 `MySQL` 启动、运行、关闭过程中的异常信息，以及严重错误（如崩溃、死锁、权限问题等）。
-   **默认位置**：数据目录下，文件名通常为 `hostname.err`。
-   **相关参数**：
    -   `log_error`：指定错误日志路径。
    -   `log_error_verbosity`：控制日志详细程度（1~3）。
-   **典型用途**：排查启动失败、崩溃原因

---

1.  查看错误日志相关参数

    ```sql
    # log_error 是日志存放地址
    SHOW VARIABLES LIKE 'log_error%';
    
    # log_error_verbosity 控制详细程度（1 仅错误，2 错误+警告，3 全部）
    ```

2.  修改错误日志详细程度（运行时生效）

    ```sql
    SET GLOBAL log_error_verbosity = 3;
    ```

3.  查看最近的错误日志（`MySQL 8.0.22+`）

    ```sql
    SELECT logged, thread_id, prio, error_code, subsystem, data
    FROM performance_schema.error_log
    ORDER BY logged DESC
    LIMIT 20;
    ```

4.  手动刷新/轮转错误日志

    ```sql
    FLUSH ERROR LOGS;
    ```

5.  命令行实时查看

    ```sql
    tail -f /var/log/mysql/error.log
    ```

6.  删除错误日志

    直接把现在的日志文件改个名备份就行

    ```shell
    mv /var/log/mysql/error.log /var/log/mysql/error-2026.09.30.log
    ```

    



# `5`. 二进制日志(`binlog`) :star:

>   二进制日志**默认开启**的

-   **作用**：记录所有**修改数据或可能修改数据**的语句（`DDL`、`DML`，不包括 `SELECT` 等只读操作），以事件形式记录并保存在**二进制文件**中。
-   **核心用途**：
    1.  **主从复制**：从库通过读取主库 `binlog` 重放实现同步。
    2.  **数据恢复**：结合全量备份 + `binlog` 做时间点恢复（`PITR`）。
    3.  **审计**：可追溯数据变更。
-   **格式（`binlog_format`）**：
    -   `STATEMENT`：记录 `SQL` 语句。
    -   `ROW`：记录每行数据的变更（推荐，更安全）。
    -   `MIXED`：混合模式。
-   **相关参数**：
    -   `log_bin`：开启 `binlog`。
    -   `binlog_format`：日志格式。
    -   `expire_logs_days` / `binlog_expire_logs_seconds`：过期自动删除。
    -   `max_binlog_size`：单个 `binlog` 文件大小上限。
-   **查看工具**：`mysqlbinlog`

---

1.  查看二进制日志相关参数

    ```sql
    # log_bin 是开关
    SHOW VARIABLES LIKE 'log_bin%';
    SHOW VARIABLES LIKE 'binlog%';
    
    # binlog_format 是日志格式（STATEMENT / ROW / MIXED）
    ```

2.  查看当前所有二进制日志文件

    ```sql
    SHOW BINARY LOGS;
    ```

3.  查看当前正在写入的二进制日志及位置

    `binlog` 的文件名好像是会不断递增的，重启一次，新建一个新的，重启一次就新建一个

    ```sql
    # 使用该命令查看现在使用的日志文件
    SHOW MASTER STATUS;
    ```

4.  手动切换/轮转二进制日志

    ```sql
    FLUSH BINARY LOGS;
    ```

5.  清理二进制日志

    ```sql
    # 按照文件名 删除掉 5 之前的，不包含 5
    PURGE BINARY LOGS TO 'mysql-bin.000005';
    
    # 根据时间删除
    PURGE BINARY LOGS BEFORE '2026-01-20 00:00:00';
    ```

    执行 `RESET MASTER;` 语句，删除所有二进制日志文件

    ```sql
    # 删库跑路的语句，别乱执行
    RESET MASTER;
    ```

6.  命令行查看二进制日志内容 `mysqlbinlog`

    `binlog` 是二进制文件，一般的 `view` 命令还看不了，需要使用 `mysqlbinlog`

    ```sql
    mysqlbinlog /var/lib/mysql/mysql-bin.000001
    
    # 不显示 binlog 格式的语句
    mysqlbinlog -v --base64-output=DECODE-ROWS /var/lib/mysql/mysql-bin.000001
    ```

    ```sql
    # sql 语句查看
    SHOW BINLOG EVENTS [IN 'log_name'] [FROM pos] [LIMIT [offset,] row_count];
    
    SHOW BINLOG EVENTS;
    
    SHOW BINLOG EVENTS IN 'binlog.000001';
    
    SHOW BINLOG EVENTS
    IN 'binlog.000001'
    FROM 126              # 从 126 位置开始
    LIMIT 0, 10;          # 查看第一页 10 行
    ```

7.  风险控制：数据库文件最好不要和 `binlog` 件放在同一个磁盘上，当数据库文件所在的磁盘发生故障时，可以使用 `binlog` 恢复数据

    可以修改配置文件 `/etc/my.cnf` 指定 `binlog` 的位置

    ```shell
    log-bin="/data/mysql/binlog/binlog"
    ```
    
    新建文件夹需要使用 `mysql` 用户
    
    ```shell
    chown -R -v mysql:mysql /data/mysql/binlog
    ```
    
    重启 `MySQL` 服务之后，新的二进制文件将会出现在 `/data/mysql/binlog` 文件夹下



## `5.2` 通过 `binlog` 恢复数据



### 用位置号 `pos` 精准重放

例如：从备份恢复的终点位置（假设是 155）开始，到事故点之前（232）停止

1.   找到 `pos`，假设找到 `155-232`

     ```sql
     # 先查看 pos，找到开始和结束的 pos
     SHOW BINLOG EVENTS
     IN 'binlog.000012';
     ```

     ```bash
     # 或者根据时间查找
     mysqlbinlog --start-datetime="2026-09-30 15:30:00" --stop-datetime="2026-09-30 16:00:00"  --verbose /data/mysql/binlog.000012
     ```

2.   开始恢复

     ```shell
     mysqlbinlog --start-position=开始的pos --stop-position=结束的pos --database=可指定数据库 日志文件 | mysql -u root -p
     
     # 举例
     mysqlbinlog --start-position=155 --stop-position=232 --database=sql_study_db /data/mysql/binlog.000012 | mysql -u root -p
     ```

原理：如果记录被 `delete`，相当于找到之前的 `insert` 语句重新 `insert`

缺点：找不到之前的 `insert` 语句，假设是3年前写的 `insert`，我上哪儿找去？



## `5.3` `binlog` 与 `redo log` 对比

-   `redo log` 它是 **物理日志**，记录内容是“在某个数据页上做了什么修改”，属于 `InnoDB` 存储引擎层产生的。
-   而 `binlog` 是 **逻辑日志**，记录内容是语句的原始逻辑，类似于“给 `ID=2` 这一行的 `c` 字段加 `1`”，属于 `MySQL Server` 层。
-   虽然它们都属于持久化的保证，但是侧重点不同。
    -   `redo log` 让 `InnoDB` 存储引擎拥有了崩溃恢复能力。
    -   `binlog` 保证了 `MySQL` 集群架构的数据一致性



## `5.4` 两阶段提交

两阶段提交是为了解决 `redo log` 和 `binlog` 在写入过程中可能出现的逻辑不一致问题，确保数据库在崩溃恢复后，数据状态依然正确



### 为什么需要两阶段提交？

假设我们要执行一条更新语句 `UPDATE T SET c=1 WHERE ID=2`。在 `InnoDB` 引擎中，更新操作会同时涉及 `redo log` 和 `binlog`。如果不用两阶段提交，而是分先后单独写入，可能会出现以下两种致命情况：

-   **情况一：先写 `redo log`，后写 `binlog`**
    如果在 `redo log` 写完后，`binlog` 还没写完时数据库崩溃了。重启后，`InnoDB` 会根据 `redo log` 恢复数据（`c` 变成了 `1`）。但是，由于 `binlog` 缺失，后续如果用这个 `binlog` 去同步从库，从库的数据就不会变。这就导致了**主从数据不一致**
-   **情况二：先写 `binlog`，后写 `redo log`**
    如果在 `binlog` 写完后，`redo log` 还没写完时数据库崩溃了。重启后，由于 `redo log` 没写成功，`InnoDB` 无法恢复这个事务（`c` 还是原值）。但是 `binlog` 已经记录了这次修改，从库同步时会执行这个修改（`c` 变成 `1`）。同样导致**主从数据不一致**



### 两阶段提交的具体流程

为了解决上述问题，`MySQL` 将 `redo log` 的写入拆成了两个步骤：`prepare` 和 `commit`，这就是“两阶段”的由来

执行一条更新语句的完整内部流程如下：

1.  **阶段一：`Prepare` 阶段**
    -   执行器先找引擎取 `ID=2` 这一行。如果数据在内存中就直接返回；否则先从磁盘读入内存
    -   执行器拿到数据后，把 `c` 的值加 `1`，得到新数据，然后调用引擎接口写入这行新数据
    -   引擎将这行新数据更新到内存中，同时将这个更新操作记录到 `redo log` 里面。**此时 `redo log` 处于 `prepare` 状态**（也就是准备状态，还没有提交）
    -   然后，执行器生成这个操作的 `binlog`，并把 `binlog` 写入磁盘。
2.  **阶段二：`Commit` 阶段**
    -   执行器调用引擎的提交事务接口
    -   引擎把刚刚写入的 `redo log` 的状态改成 `commit`（提交）状态，更新完成



# `6`. 中继日志(`relay log`)

-   **作用**：只在主动复制的**从库**有，**从库（`Slave/Replica`）专用**。从库的 `I/O` 线程把主库 `binlog` 事件写入 `relay log`，`SQL` 线程再读取 `relay log` 重放。
-   **特点**：结构类似 `binlog`，由从库自动管理，一般无需手动干预。
-   **相关参数**：`relay_log`、`relay_log_purge`。

---

1.  查看中继日志相关参数

    ```sql
    SHOW VARIABLES LIKE '%relay%';
    ```

2.  查看从库复制状态（含中继日志信息）

    ```sql
    SHOW SLAVE STATUS\G;
    # 关注 Relay_Log_File、Relay_Log_Pos、Relay_Master_Log_File
    ```

3.  查看中继日志事件

    ```sql
    SHOW RELAYLOG EVENTS IN 'relay-bin.000001' FROM 123 LIMIT 10;
    ```

4.  清理中继日志

    ```sql
    PURGE RELAY LOGS BEFORE '2026-01-20 00:00:00';
    ```

5.  临时禁用自动清理

    ```sql
    SET GLOBAL relay_log_purge = 0;
    ```
