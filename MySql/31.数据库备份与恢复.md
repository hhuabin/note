# 数据库备份与恢复

## `1`. 为什么需要备份

-   **硬件故障**：磁盘损坏、服务器宕机
-   **人为误操作**：误删表、误更新、DROP 数据库
-   **软件/逻辑错误**：程序 Bug 写入脏数据
-   **灾难事件**：火灾、水灾、勒索病毒
-   **合规要求**：等保、审计、行业监管



## `2`. 物理备份与逻辑备份

**物理备份**：备份数据文件，转储数据库物理文件到某一目录。物理备份恢复速度比较快，但占用空间比较大，`MySQL` 中可以用 `xtrabackup` 工具来进行物理备份。

**逻辑备份**：对数据库对象利用工具进行导出工作，汇总入备份文件内。逻辑备份恢复速度慢，但占用空间小，更灵活。`MySQL` 中常用的逻辑备份工具为 `mysqldump`。逻辑备份就是 **备份 `sql` 语句**，在恢复的时候执行备份的 `sql` 语句实现数据库数据的重现。



## `3`. `mysqldump` 实现逻辑备份

### `3.1` 备份一个数据库

`mysqldump` 命令执行时，可以将数据库备份成一个 **文本文件**，该文件中实际上包含多个 `CREATE` 和 `INSERT` 语句，使用这些语句可以重新创建表和插入数据

```shell
mysqldump -uroot -p 数据库名 > 备份文件名称.sql

# 举例
mysqldump -uroot -p sql_study_db > ./backup/sql_study_db_2026.10.08.sql
```



### `3.2` 备份全部数据库

```shell
mysqldump -uroot -p --all-databases > 备份文件名称.sql
mysqldump -uroot -p -A > 备份文件名称.sql

# 举例
mysqldump -uroot -p --all-databases > ./backup/all_databases_2026.10.08.sql
```



### `3.3` 备份部分数据库

```shell
mysqldump -u user -h host -p --databases [数据库的名称1 [数据库的名称2...]] > 备份文件名称.sql

# 举例
mysqldump -uroot -p --databases sql_study_db sql_study_db2 >two_database.sql
mysqldump -uroot -p -B sql_study_db sql_study_db2 >two_database.sql
```



### `3.4` 备份部分表

```shell
mysqldump -u user -h host -p 数据库的名称 [表名1 [表名2...]] > 备份文件名称.sql

# 举例
mysqldump -uroot -p sql_study_db book> book.sql
```



### `3.5` 备份单表的部分数据

`--where`

```shell
备份 student 表中 id 小于 10 的数据
mysqldump -uroot -p sql_study_db student --where="id < 10 " > student_part_id10_low_bak.sql
```



### `3.6` 排除部分表

`--ignore-table`

```shell
mysqldump -uroot -p sql_study_db --ignore-table = sql_study_db.student > no_student_bak.sql
```



## `4`. `mysql` 命令恢复数据库



### `4.1` 单库备份中恢复单库

```shell
# 备份文件中包含创建数据库的语句
mysql -uroot -p < ./backup/sql_study_db_2026.10.08.sql

# 备份文件中不包含创建数据库的语句，需要指定数据库
mysql -uroot -p sql_study_db < ./backup/sql_study_db_2026.10.08.sql
```

`SOURCE` 好像也行，都可以试试

```sql
# 如果 sql 文件里没有建库语句，需先建库：
CREATE DATABASE db_name;

USE 数据库名;
SOURCE /path/to/表名.sql;
```



### `4.2` 全量备份恢复

```shell
mysql -uroot -p < ./backup/all_databases_2026.10.08.sql
```



### `4.3` 从全量备份中恢复单库

```shell
# 1. 先确认标记存在
grep -n "Current Database" ./backup/all_databases_2026.10.08.sql

# 2. 截取 sql_study_db 这一段的 SQL（从当前库标记到下一个库标记之前）
sed -n '/^-- Current Database: `sql_study_db`/,/^-- Current Database: `/p' ./backup/all_databases_2026.10.08.sql > ./backup/mydb_only.sql

# 3. 但上面会把下一个库的标记行也带进来，需要去掉最后一行
sed -i '$d' ./backup/mydb_only.sql

# 4. 恢复前先建库（如果文件里没带 CREATE DATABASE）
mysql -uroot -p -e "CREATE DATABASE IF NOT EXISTS sql_study_db DEFAULT CHARACTER SET utf8mb4;"

# 5. 导入单库
mysql -uroot -p mydb < ./backup/mydb_only.sql
```



### `4.4` 从单库备份中恢复单表

```shell
# 1. 确认表标记存在
grep -n "Table structure for table \`orders\`" ./backup/mydb_2026.10.08.sql

# 2. 截取 orders 表这一段（从表结构标记到下一张表标记之前）
sed -n '/^-- Table structure for table `orders`/,/^-- Table structure for table `/p' \
  ./backup/mydb_2026.10.08.sql > ./backup/orders_only.sql

# 3. 去掉最后多带进来的下一张表标记行
sed -i '$d' ./backup/orders_only.sql

# 4. 检查截取结果（应包含 DROP、CREATE、INSERT）
cat ./backup/orders_only.sql | head -n 30
grep -c "INSERT INTO" ./backup/orders_only.sql

# 5. 恢复
mysql -uroot -p mydb < ./backup/orders_only.sql
```



## `5`. 物理备份：直接复制整个数据库

| 方式             | 做法                                                   | 能否热备             |
| :--------------- | :----------------------------------------------------- | :------------------- |
| **冷备份**       | 停库 → `cp`/`tar` → 启库                               | ❌ 必须停库，业务中断 |
| **热备份**       | 用工具（`XtraBackup` / `pg_basebackup`）在库运行时备份 | ✅ 不停库             |
| **文件系统快照** | `LVM`/云盘快照，秒级、一致性由存储层保证               | ✅ 短暂停顿           |



### `5.1` `MySQL` 冷备份与恢复

>   备份与恢复的 `MySQL` 主版本必须一样
>
>   仅适用于 `MyISQM` 的表，对于 `InnoDB` 没用，也就是说，总体没啥用，还是使用逻辑备份吧

1.   停库备份

     ```shell
     # 1. 停库
     systemctl stop mysqld
     
     # 2. 复制整个 datadir（含配置文件更保险）
     cp -ra /data/mysql /backup/mysql_cold_2026.10.08
     cp /etc/my.cnf /backup/mysql_cold_2026.10.08/
     
     # 3. 启库
     systemctl start mysqld
     ```

2.   全局锁备份

     ```sql
     # 加全局读锁
     FLUSH TABLES WITH READ LOCK;
     
     cp -ra /data/mysql /backup/mysql_cold_2026.10.08
     cp /etc/my.cnf /backup/mysql_cold_2026.10.08/
     
     # 解锁
     UNLOCK TABLES;
     ```
     

---

恢复

```shell
systemctl stop mysqld

rm -rf /data/mysql/*
cp -ra /backup/mysql_cold_2026.10.08/mysql/* /data/mysql/

# 权限配置
chown -R mysql:mysql /data/mysql

systemctl start mysqld
```



## `6`. 表的导出

### `6.1` `INTO OUTFILE` 导出

```sql
SELECT 列1, 列2, ...
FROM 表名
[WHERE 条件]
INTO OUTFILE '文件路径'
# 下面的一般不需要写
[FIELDS
    [TERMINATED BY '字段分隔符']
    [[OPTIONALLY] ENCLOSED BY '包围符']
    [ESCAPED BY '转义符']
]
[LINES
    [STARTING BY '行起始符']
    [TERMINATED BY '行结束符']
];
```

1.   `mysql` 默认对导出的目录有权限控制，也就是说使用命令进行导出的时候，需要指定目录进行操作

     查询 `secure_file_priv` 的值

     ```sql
     SHOW GLOBAL VARIABLES LIKE '%secure%';
     ```

     如果 `secure_file_priv` 值为空，则可以导出到任何目录（这是不安全的），否则只能导出到 `secure_file_priv` 指定目录，或者其子目录下

2.   导出 `CSV`

     ```sql
     SELECT *
     FROM `user`
     INTO OUTFILE '/usr/local/mysql-8.0.46-linux-glibc2.28-x86_64/mysql-files/back.csv'
     FIELDS TERMINATED BY ','
     OPTIONALLY ENCLOSED BY '"'
     LINES TERMINATED BY '\n';
     ```

     下载 `back.csv`，用 Excel 双击打开即可



### `6.2` 使用 `mysql` 命令导出本地文件

这个导出的文件目录好像没有限制

```shell
mysql -u root -p -e "SELECT * FROM db.table" > /data/result.csv
```



### `6.3` 使用 `mysqldump` 命令导出本地文件

```shell
mysqldump -uroot -p -T "secure_file_priv 指定目录" 数据库名 表名

# 举例
mysqldump -uroot -p -T "/usr/local/mysql-8.0.46-linux-glibc2.28-x86_64/mysql-files" sql_study_db user_test
```

默认生成两个与表同名的文件，一个 `.sql` 一个 `.txt`



## `7`. 表的导入

### `7.1` 使用 `LOAD DATA INFILE` 导入本地文件

>   导入 `.txt` 文件好使，导入 `.csv` 文件会因为表头的问题失败

```shell
LOAD DATA INFILE '/usr/local/mysql-8.0.46-linux-glibc2.28-x86_64/mysql-files/back.txt' INTO TABLE sql_study_db.user_test
```



### `7.2` 使用 `mysqlimport` 导入本地文件

```shell
# 文件民最好和表名一致
mysqlimport -uroot -p 数据库名 '文件名'

# 表名使用过 user_test（去掉.txt的结果）
mysqlimport -uroot -p sql_study_db '/usr/local/mysql-8.0.46-linux-glibc2.28-x86_64/mysql-files/user_test.txt'
```



## `8`. 数据库迁移

数据迁移（`data migration`）是指选择、准备、提取和转换数据，并**将数据从一个计算机存储系统永久地传输到另一个计算机存储系统的过程**。此外，**验证迁移数据的完整性**和**退役原来旧的数据存储**，也被认为是整个数据迁移过程的一部分



### `8.1` 迁移方案

`MySQL` 的迁移方案大致可以分为 **物理迁移** 和 **逻辑迁移**

##### 物理迁移

需要停机迁移

##### 逻辑迁移

逻辑迁移适用范围更广，无论是 **部分迁移** 还是 **全量迁移** ，都可以使用逻辑迁移。逻辑迁移中使用最多的就是通过 `mysqldump` 等备份工具

```mermaid
graph LR
    Root[数据迁移] --- Phys[物理迁移]
    Root --- Logi[逻辑迁移]

    Phys --- P1[适用场景：大数据量下的整体迁移]
    Phys --- P2[优点：迁移速度快]
    Phys --- P3[缺点：需停机、不灵活、可能有位置错误]

    Logi --- L1[适用场景：各种场景]
    Logi --- L2[优点：兼容性高、灵活方便、可跨版本]
    Logi --- L3[缺点：迁移时间长]
    
    Logi --- Sug[几点建议]
    Sug --- S1[排除不需要迁移的表]
    Sug --- S2[大表可以单独处理]
    Sug --- S3[注意数据库用户权限问题]
    Sug --- S4[迁移后要核实]
```

### `9.1` `delete` 误删

### `9.2` `truncate / drop` 误删

使用 **全量备份** 与 **增量日志** 结合的方式处理

1.  取最近一次 **全量备份**。假设设置数据库库是一天一备，最近备份数据是当天 **凌晨2点**；
2.  用备份恢复出一个 **临时库**； （注意：这里选择临时库，而不是直接操作主库，怕其他恢复操作影响主库）
3.  取出凌晨2点之后的 `binlog` 日志；
4.  剔除误删除数据的语句外，其它语句全部应用到临时库。 [`binlog` 恢复数据](./29.其他数据库日志.md#`5.2` 通过 `binlog` 恢复数据 "`binlog` 恢复数据")
5.  最后恢复到主库
