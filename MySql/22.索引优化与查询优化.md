# `1`. 索引失效的情况

| 案例                      | SQL                                  | 说明                                             |
| ------------------------- | ------------------------------------ | ------------------------------------------------ |
| 联合索引违反最左匹配      | `(a,b,c)`，查询 `WHERE b=10`         | 缺少最左列 `a`                                   |
| 对索引列做函数            | `WHERE YEAR(create_time) = 2026`     | 对列计算后再比较，普通索引难以直接定位           |
| 对索引列进行运算          | `WHERE price + 10 > 100`             | 索引列参与运算                                   |
| 隐式类型转换              | `WHERE user_id = '1001'`             | 字符串与数值类型不一致，可能发生类型转换         |
| 范围查询右边的列索引失效  | `(a,b,c)`，`WHERE a > 10 AND b = 20` | `a` 使用范围后，`b` 通常不能继续用于缩小索引范围 |
| `LIKE` 左模糊             | `WHERE name LIKE '%张'`              | 前面是 `%`，无法确定索引从哪里开始               |
| 使用 `OR`                 | `WHERE user_id = 100 OR age = 20`    | `OR` 两边没有合适索引时，可能放弃索引            |
| `!=` / `<>` 不等于        | `WHERE status != 1`                  | 匹配范围可能太大，优化器可能认为全表扫描更快     |
| `IS NULL` / `IS NOT NULL` | `WHERE name IS NOT NULL`             | 不一定失效，但可能因为选择性太低而不使用         |
| `NOT IN`                  | `WHERE status NOT IN (1,2)`          | 同样可能导致扫描大量数据                         |
| 查询返回大量数据          | `WHERE status = 1`，但 90% 都是 `1`  | 索引选择性低，优化器可能选择全表扫描             |
| 数据量太小                | 表只有几十行                         | 全表扫描可能比走索引更快                         |

1.   联合索引倾向使用更长的

     有索引 `(a, b, c)` 和索引 `(a, b)`

     ```sql
     SELECT * FROM employees
     WHERE a = 1, b = 2, c = 3;
     ```

     会使用 `(a, b, c)` 而不会使用 `(a, b)`，所以创建联合索引时，创建长的即可，短的可以删掉

2.   联合索引违反最左匹配

     有索引 `(a, b, c)` 

     ```sql
     SELECT * FROM employees
     WHERE a = 1, c = 3;
     ```

     缺少 `b`，索引 `(a, b, c)`  只有 `a` 会生效，`c` 用不了这个联合索引

3.   主键插入顺序

     已有 `id: 1, 3, 5, 7, 9...`，插入个 `6` 进来，无序，违反 聚簇索引 顺序规则，容易造成 **页分裂**

4.   计算、函数、类型转换（自动或手动）导致索引失效

     ```sql
     # 不推荐，做了运算之后不能使用 create_time 的索引
     SELECT *
     FROM orders
     WHERE YEAR(create_time) = 2026;
     
     # 可以改成这样，可以使用create_time的索引
     SELECT *
     FROM orders
     WHERE create_time >= '2026-01-01'
       AND create_time < '2027-01-01';
     ```

     ```sql
     CREATE TABLE user (
         id BIGINT,
         name VARCHAR(50)
     );
     
     # 类型转换导致索引失效，这里是隐士转换
     SELECT *
     FROM user
     WHERE id = '100';
     ```

5.   对于联合索引，范围查询右边的列索引失效

     对于联合索引 `(a, b, c)`

     ```sql
     SELECT *
     FROM user
     WHERE a > 10
       AND b = 20
       AND c = 30;
     ```

     但 `a` 已经变成一个范围。后面的 `b`、`c` 通常不能像 `a` 那样继续用于缩小 `B+Tree` 的扫描范围

     解决方式：创建索引时使用 `(b, c, a) idx_b_c_a`，把 `a` 索引放到最后即可

6.   不等于 `!=` / `<>` 索引失效

     ```sql
     SELECT *
     FROM user
     WHERE status != 1;
     ```

     走等于可以很好的利用索引；走不等于，不等于的数据量占比可能非常高，如（1，2，3，4，5，6，7），不等于1的占比远多于10%，走索引还不如直接扫描表

7.   `IS NULL` 可以使用索引，`IS NOT NULL` 无法使用索引

     ```sql
     SELECT *
     FROM user
     WHERE status IS NOT NULL;
     ```

     情况和 6 类似，`IS NOT NULL` 的占比也可能很多

8.   `LIKE` 以通配符 `%` 开头的索引失效

     ```sql
     WHERE name LIKE '%张'
     
     # 这个可以使用索引
     WHERE name LIKE '张%'
     ```

     数据库不知道 `"张"` 在字符串的什么位置，因此普通 `B+Tree` 索引很难直接定位

9.   `OR` 前后存在非索引的列，索引失效

     ```sql
     CREATE INDEX idx_user_id ON user(user_id);
     
     SELECT *
     FROM user
     WHERE user_id = 100 OR age = 20;
     ```

     因为只有一个索引，又是 `OR`，哪怕 `user_id` 用了索引，`age  = 20` 还是要全表扫描，不如干脆全表扫描

     解决办法：分别建立两个单列索引，**注意不能使用联合索引 `(user_id, age)`**，联合索引更适用于 `AND`

     ```sql
     CREATE INDEX idx_user_id ON user(user_id);
     CREATE INDEX idx_age ON user(age);
     ```

10.   使用统一的字符集 `utf8mb4` 或 `utf8mb3`，不同的字符集进行比较需要转换可能会造成乱码和索引失效

11.   联合索引使用情况

      假设联合索引为：`INDEX(a, b, c)`

      | Where语句                                                    | 索引是否被使用                                               |
      | ------------------------------------------------------------ | ------------------------------------------------------------ |
      | `WHERE a = 3`                                                | Y，使用到 `a`                                                |
      | `WHERE a = 3 AND b = 5`                                      | Y，使用到 `a、b`                                             |
      | `WHERE a = 3 AND b = 5 AND c = 4`                            | Y，使用到 `a、b、c`                                          |
      | `WHERE b = 3` 或者 `WHERE b = 3 AND c = 4` 或者 `WHERE c = 4` | N                                                            |
      | `WHERE a = 3 AND c = 5`                                      | 使用到 `a`，但是 `c` 不可以，`b` 中间断了                    |
      | `WHERE a = 3 AND b > 4 AND c = 5`                            | 使用到 `a` 和 `b`，`c` 不能在范围之后使用，`b` 断了          |
      | `WHERE a IS NULL AND b IS NOT NULL`                          | `IS NULL` 支持索引，但是 `IS NOT NULL` 不支持。所以 `a` 可以使用索引，但是 `b` 不可以使用 |
      | `WHERE a <> 3`                                               | 不能使用索引                                                 |
      | `WHERE ABS(a) = 3`                                           | 不能使用索引                                                 |
      | **`WHERE a = 3 AND b LIKE 'kk%' AND c = 4`**                 | Y，使用到 `a、b、c`                                          |
      | `WHERE a = 3 AND b LIKE '%kk' AND c = 4`                     | Y，只用到 `a`                                                |
      | `WHERE a = 3 AND b LIKE '%kk%' AND c = 4`                    | Y，只用到 `a`                                                |
      | **`WHERE a = 3 AND b LIKE 'k%kk%' AND c = 4`**               | Y，使用到 `a、b、c`                                          |



# `2`. 关联查询的优化

| `JOIN`       | 典型索引重点                                        |
| ------------ | --------------------------------------------------- |
| `INNER JOIN` | `JOIN` 两边都可以建立索引，通常重点关注被查找的一侧 |
| `LEFT JOIN`  | **优先关注右表 `JOIN` 字段**                        |
| `RIGHT JOIN` | **优先关注左表 `JOIN` 字段**                        |



## `2.1` 左外连接

```sql
# 查询所有用户，以及每个用户对应的订单
SELECT *
FROM `user`
LEFT JOIN orders ON `user`.id = orders.user_id;

# 左表：user
# 右表：orders
```

优先关注**右表（被驱动表）** `JOIN` 字段的索引。左外连接中，左表的数据本来就是全都要的，因此左表连接字段通常没有右表连接字段那么重要



## `2.2` 内连接

内连接驱动表：在内连接中，`MySQL` 优化器可以根据**成本（结果集大小）**选择驱动表，通常情况下，会倾向于**小表驱动大表**，小表会作为驱动表，大表作为被驱动表，以减少后续 `JOIN` 的查找次数

```sql
# 查询所有用户，以及每个用户对应的订单
SELECT *
FROM `user`
INNER JOIN orders ON `user`.id = orders.user_id;
```

一般来说，`user.id` 和 `orders.user_id` 两边都需要建立索引

如果只能建立一个索引，**谁结果集大就建立谁的索引**，有索引的表查询数据快，将会作为被驱动表



## `2.3` 右外连接

```sql
SELECT *
FROM `user`
LEFT JOIN orders ON `user`.id = orders.user_id;
```



## `2.4` `JOIN` 原理

```sql
SELECT *
FROM `user`
LEFT JOIN orders ON `user`.id = orders.user_id;
```

| 算法                    | 内表怎么查   | 是否需要内表索引 | 核心思想               |
| ----------------------- | ------------ | ---------------- | ---------------------- |
| **简单嵌套循环 `NLJ`**  | 每次全表扫描 | ❌                | 一条一条地匹配         |
| **索引嵌套循环 `INLJ`** | 使用索引查找 | ✅                | 一条一条地通过索引查找 |
| **块嵌套循环 `BNLJ`**   | 批量扫描     | ❌                | 一批外表数据一起匹配   |



### `2.4.1` 简单嵌套循环连接 `NLJ`

`Nested-Loop Join`：简单嵌套循环连接 = 外表每一行，都把内表完整扫描一遍（`O(M * N)`）

```sql
遍历外表
    ↓
拿一条数据
    ↓
遍历整个内表
    ↓
寻找匹配数据
    ↓
再拿外表下一条
```

`user` 100 条，`orders` 10000 条，大约需要100 × 10000 = 100万次比较



### `2.4.2` 索引嵌套循环连接 `INLJ`

`Index Nested-Loop Join`：内表有索引，不再每次扫描整个内表，而是通过索引查找

```sql
CREATE INDEX idx_orders_user_id
ON orders(user_id);
```

```sql
外表 user
    ↓
取一条
    ↓
拿 user.id
    ↓
使用 orders.user_id 索引
    ↓
找到匹配订单
```

比 `O(M * N)` 高效得多



### `2.4.3` 块嵌套循环连接 `BNLJ`

`Block Nested-Loop Join`：一次把一批外表记录**放进内存 `Join Buffer`**，然后扫描一次内表，用这一批数据一起匹配

```sql
# 假设 user 10000 条，每次拿 100 条
第1批：
user 1 ~ 100
        ↓
扫描 orders 一次

第2批：
user 101 ~ 200
        ↓
扫描 orders 一次

第3批：
user 201 ~ 300
        ↓
扫描 orders 一次

...
```

这样就减少了对 `orders` 的重复扫描

>   有必要可以减少查询的字段，让 `Join Buffer`

>   ```sql
>   # 查看 join_buffer 的大小，默认是 256K
>   SHOW VARIABLES LIKE 'join_buffer_size';
>   SELECT @@session.join_buffer_size;
>   SELECT @@global.join_buffer_size;
>   
>   # 设置当前会话为 1MB，如果需要全局修改，可以改配置文件，最大可以申请 4G
>   SET SESSION join_buffer_size = 1024 * 1024;
>   ```





# `3`. 子查询优化

```sql
SELECT *
FROM user
WHERE id IN (
    SELECT user_id     # 子查询
    FROM orders
    WHERE amount > 1000
);
```

子查询是 `MysQL` 的一项重要的功能，可以帮助我们通过一个 `SQL` 语句实现比较复杂的查询。但是，子查询的执行效率不高

1.   执行子查询时，`MysQL` 需要为内层查询语句的查询结果建立一个**临时表**，然后外层查询语句从临时表中查询记录。查询完毕后，再撒销这些临时表。这样会消耗过多的 `CPU` 和 `I0` 资源，产生大量的慢查询
2.   子查询的结果集存储的临时表，不论是内存临时表还是磁盘临时表都**不会存在索引**，所以查询性能会受到一定的影响
3.   对于返回结果集比较大的子查询，其对查询性能的影响也就越大

>   结论：尽量让子查询少执行、少扫描数据，并在合适的情况下把子查询改写成 `JOIN`、`EXISTS` 等形式
>
>   不过要注意：**不是看到子查询就一定要改成 `JOIN`**。`MySQL` 优化器本身会对部分子查询进行优化



### 子查询改成 `JOIN`

```sql
SELECT *
FROM `user`
WHERE id IN (
    SELECT user_id
    FROM orders
    WHERE amount > 1000
);

# 使用 `JOIN` 改写成
SELECT DISTINCT `user`.*
FROM `user`
JOIN orders
    ON `user`.id = orders.user_id
WHERE orders.amount > 1000;
```

尽量不要使用 `NOT IN` 或者 `NOT EXISTS`，用 `LEFT JOIN xxx ON xx WHERE xx IS NULL` 替代



### `IN` 和 `EXISTS`

```sql
# 查询该用户有没有订单
SELECT *
FROM `user`
WHERE `user`.id IN (
    SELECT orders.user_id
    FROM orders
);

# 如果 orders 表比较大，可以使用 EXISTS 改写成
SELECT *
FROM `user`
WHERE EXISTS (
    SELECT 1
    FROM orders
    WHERE orders.user_id = `user`.id
);
```

最终的目的都是 **减少扫描**



# `4`. 排序优化

在 `MysQL` 中，支持两种排序方式，分别是 `FileSort` 和 `Index` 排序

1.   `Index` 排序中，索引可以保证数据的有序性，不需要再进行排序，效率更高

2.   `FileSort` 排序则一般在**内存中**进行排序，占用 `CPU` 较多。

     如果**待排结果较大**，会产生临时文件 `I/0` 到磁盘进行排序的情况，效率较低。

     如果**待排结果较小**，`FileSort` 排序也非常快

优化建议：

1.   在 `ORDER BY` 中应尽量避免使用 `FileSort` 排序
2.   尽量使用 `Index` 完成 `ORDER BY` 排序。如果 `WHERE` 和 `ORDER BY` 后面是相同的列就使用单索引列，如果不同就使用联合索引
3.   无法使用 `Index` 时，需要对 `FileSort` 方式进行调优



### `4.1` 创建排序列的索引

```sql
# Extra 中出现 Using filesort
EXPLAIN
SELECT salary
FROM employees
ORDER BY salary;

# 解决
CREATE INDEX idx_salary
ON employees(salary);
```

>   注意，如果 `SELECT *` 的话，创建索引后，还是可能使用 `Using filesort`。原因如下：
>
>   1.   `SELECT *` 导致回表成本太高的话
>   2.   表数据量太小，比如只有几十行，直接加载全表到内存，使用 `全表扫描 → 排序` 也非常快，省去了走索引再回表
>   3.   **减少回表成本**解决该问题，如 `SELECT salary`；或者使用 `LIMIT 10` 减少查询到的回表



### `4.2` `ORDER BY` 顺序错误，索引失效

在联合索引中的顺序问题，也遵循最佳左前侧原则。假设有索引 `(a, b, c)`

1.   `ORDER BY b` 肯定用不了联合索引
2.   `ORDER BY a DESC, b ASC`，a 是降序，b 是升序，反序了，用不了索引；可以考虑使用 **降序索引 `(a DESC, b ASC)`**
3.   `ORDER BY a ASC, b DESC`，a、b 反序，也不能用索引
4.   `ORDER BY a DESC, b DESC`，a、b 同序，这个可以用
5.   总结：能不能用上索引，是基于 **执行成本** 决定的，包括**数据量、回表**等成本



### `4.3` `FileSort` 算法：双路排序和单路排序

-   双路排序：第一次只排序“排序字段 + 行定位信息”，排序完成后，再根据行定位信息**回表**获取完整数据

    第一路：读取 + 排序

    第二路：根据排序结果回表取数据

-   单路排序：把排序字段 + 查询需要返回的字段一起放进排序区，排序完成后直接返回，不需要再次回表

    优点：减少回表 I/O

    缺点：排序时需要保存更多数据

```sql
# 查询排序缓冲区大小，默认是 256K
SHOW VARIABLES LIKE 'sort_buffer_size';
SELECT @@session.sort_buffer_size;
SELECT @@global.sort_buffer_size;

# 设置当前会话为 1MB，如果需要全局修改，可以改配置文件
SET SESSION sort_buffer_size = 1024 * 1024;
```



# `5`. `GROUOP BY` 优化

1.   `group by` 使用索引的原则几乎跟 `order by` 一致，`group by` 即使没有过滤条件用到索引，也可以直接使用索引。
2.   `group by` 先排序再分组，遵照索引建立的最左前缀法则
3.   当无法使用索引列，增大 `max_length_for_sort_data` 和 `sort_buffer_size` 参数的设置
4.   **`where` 效率高于 `having`**，能写在 `where` 限定的条件就不要写在 `having` 中了
5.   减少使用 `order by`，和业务沟通能不排序就不排序，或将**排序放到程序端**（工资不到位就不要管那么多了）做。`Order by`、`group by`、`distinct` 这些语句较为耗费 `CPU`，数据库的 `CPU` 资源是极其宝贵的。
6.   包含了 `order by`、`group by`、`distinct` 这些查询的语句，`where` 条件过滤出来的结果集请保持在 1000 行以内，否则 `SQL` 会很慢。



# `6`. 优化分页查询 `LIMIT`

```sql
SELECT *
FROM student
LIMIT 2000000, 10;
```

对于 `LIMIT 2000000, 10` 只要 2000000 - 2000010 的记录，其他的丢弃，查询排序的代价非常大，这时候可以巧妙利用自增 `id` 处理

```sql
SELECT *
FROM student
WHERE id > 2000000
LIMIT 10;
```

这样处理数据会存在不准的情况，比如某条数据被删了，但是都到 2000000 谁还关注那一两条的删除。对于极度需要精准的数据，慎用



# `7`. 优先考虑覆盖索引

**覆盖索引**：查询需要的数据，**索引里已经全部包含**了，所以 `MySQL` 不需要再**回表**查询数据



### 回表 `Table Lookup`

```sql
CREATE INDEX idx_salary
ON employees(salary);

SELECT *
FROM employees
WHERE salary = 5000;
```

```sql
# 普通索引查询流程
idx_salary
    ↓
找到 salary = 5000
    ↓
得到 id = 1
    ↓
根据 id = 1
    ↓
回到聚簇索引
    ↓
找到完整记录
```

**二级索引 → 聚簇索引** 的过程，就叫**回表**



## `7.1` 覆盖索引

覆盖索引的本质：查询所需要的字段，是否全部能够从索引中直接获得

```sql
SELECT salary
FROM employees
WHERE salary = 5000;
```

>   只查 `salary`，根据 `idx_salary` 找到 `salary = 5000`，直接返回 `salary`，根本不需要回表，这就是覆盖索引
>
>   所以，`SELECT *` 通常很难形成覆盖索引



### 覆盖索引和联合索引

覆盖索引经常和**联合索引**一起使用

```sql
CREATE INDEX idx_user_status_time
ON orders(user_id, status, create_time);

# 完美的覆盖索引使用情况，查询的都是条件需要的
SELECT user_id, status, create_time
FROM orders
WHERE user_id = 1001
  AND status = 1
ORDER BY create_time DESC;
```

>   由于覆盖索引可以减少树的搜索次数，显著提升查询性能，所以使用覆盖索引是一个常用的性能优化手段
>
>   但是不要为了覆盖索引疯狂加字段，比如`idx_a_b_c_d`，索引越大，占用磁盘空间，维护索引的成本也会上升



# `8`. 索引下推 `ICP`

索引下推(`Index Condition Pushdown`，`ICP`)：把原本需要“回表后才能判断”的部分 `WHERE` 条件，下推到存储引擎的索引层，在回表之前先过滤掉不符合条件的记录，从而**减少回表次数**

```sql
# 查看索引下推的开启状态，通常默认都是开启状态 index_condition_pushdown=on
SHOW VARIABLES LIKE 'optimizer_switch';
SELECT @@session.optimizer_switch;
SELECT @@global.optimizer_switch;

# 当前会话关闭
SET SESSION optimizer_switch = 'index_condition_pushdown=off';
# 开启
SET SESSION optimizer_switch='index_condition_pushdown=on';
```



### 索引下推举例

```sql
CREATE TABLE employees (
    id INT PRIMARY KEY,
    name VARCHAR(50),
    age INT,
    department_id INT
);

CREATE INDEX idx_name_age
ON employees(name, age);

SELECT *
FROM employees
WHERE name LIKE '张%' AND age = 20;
```

>   `name LIKE '张%'` 是一个范围条件，所以传统的索引使用方式可能无法继续利用 `age` 来缩小索引扫描范围
>
>   开启索引下推后：索引 -> `name LIKE '张%'` -> 在索引层继续判断 `age = 20` -> 只有符合条件的记录 -> 回表
>
>   `ICP` 最大的价值：减少回表

```sql
# Extra 中看到 Using index condition 就是使用了索引条件下推
EXPLAIN
SELECT *
FROM employees
WHERE name LIKE '张%' AND age = 20;
```



 哪些情况可能使用 `ICP`

1.   范围条件后还有索引列：`WHERE a = 1 AND b > 10 AND c = 20`
2.   `LIKE` 范围后还有索引列：`WHERE a = 1 AND b LIKE 'abc%' AND c = 20`



# `9`. 其他查询优化策略

## `9.1` `COUNT(*)`、`COUNT(1)`、`COUNT(IFNULL(具体字段, 0)`效率对比

1.   `COUNT(*)`、`COUNT(1)` 都是对所有结果进行 `COUNT`，本质上没有区别

     `InnoDB` 的 `COUNT(*)`、`COUNT(1)` 需要扫面全表，复杂度是 `O(n)`

     `MyISAM` 维护了一个 `row_count` 字段，所以复杂度是 `O(1)`

2.   如果非要采用 `COUNT(IFNULL(具体字段, 0)` 方式来统计行数，要尽量采用二级索引，聚簇索引包含的信息更多，明显大于二级索引；`COUNT(*)`、`COUNT(1)` 会自动采用占用空间更小的二级索引来进行统计



## `9.2` `SELECT *`

在表查询中，建议明确字段，不要使用 `*` 作为查询的字段列表，推荐使用 `SELEcT<字段列表>` 查询。

1.   `MySQL` 在解析的过程中，会通过查询数据字典将 `*` 按序转换成**所有列名**，这会大大的耗费资源和时间
2.   无法使用覆盖索引



## `9.3` `LIMIT 1` 对优化的影响

针对的是会扫描全表的 `SQL` 语句，如果你可以确定结果集只有一条，那么加上 `LIMIT 1` 的时候，当找到一条结果的时候就不会继续扫描了，这样会加快查询速度

如果数据表已经对字段建立了唯一索引，那么可以通过**唯一索引进行查询**，不会全表扫描的话，就不需要加上 `LIMIT 1` 了。



## `9.4` 多使用 `COMMIT`

只要有可能，在程序中尽量多使用 `COMMIT`，这样程序的性能得到提高，需求也会因为 `COMMIT` 所释放的资源而减少

`COMMIT` 所释放的资源：

1.   回滚段上用于恢复数据的信息
2.   被程序语句获得的锁
3.   `redo/undo log buffer` 中的空间
4.   管理上述3种资源中的内部花费



# `10`. 主键设计

## `10.1` 自增 `id`

```sql
id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY COMMENT '主键ID'
```

- 优点：简单直接
- 缺点：
  1. 可靠性不高，自增 `ID` 存在回溯的情况，`MySQL 8.0` 已修复
  2. 安全性不高，自增 `ID` 很容易被攻击者猜出来
  3. 性能差：自增 `ID` 性能较差，需要在数据库服务器端生成
  4. 交互多：业务需要执行一次类似 `last_insert_id()` 函数才能知道刚才插入的值，每一次 `sql` 交互都是耗费巨大的
  5. 局部唯一性：分布式数据库用不了



## `10.2` `UUID`

> 全局唯一性：在 `UUID` 中时间部分占用 60 位，存储的类似 `TIMESTAMP` 的时间戳，但表示的是从 `1582-10-15 00:00:00.00` 到现在的 10ons 的计数。
>
> 可以看到UUID存储的时间精度比 `TIMESTAMPE` 更高，时间维度发生重复的概率降低到 1/100ns。
>
> 时钟序列是为了避免时钟被回拨导致产生时间重复的可能性。`MAC` 地址用于全局唯一。

```sql
SELECT UUID() FROM DUAL;
# 3ac1cf0d-b100-11f1-b3f2-005056c00001
#    8    + 4  + 4  + 4  +   12
# 32字节英文 + 4字节`-` = 36 字节字符串
```

> `UUID` 的组成： 16 字节时间+版本，4字节时钟序列，12字节`MAC`地址
>
> 16字节时间+版本：一字节4位，共64位数；其中32位时间低位 + 16位时间中位 + 12 位时间高位 + 4位 `UUID`版本

`UUID` 是随机无序的：因为 `UUID` 的设计中，将时间低位放在最前面，而这部分的数据是一直在变化的，并且是无序



### 改造成有序的 `UUID`

```sql
# 通过 uuid_to_bin(UUID(), TRUE) 将 UUID 转化为有序的 UUID
SELECT uuid_to_bin(UUID(), TRUE) FROM DUAL;

# 验证有序
SET @uuid = UUID();
SELECT @uuid, uuid_to_bin(@uuid), uuid_to_bin(@uuid, TRUE) FROM DUAL;
```

> 1. 若将时间高低位互换，则时间就是单调递增的了，也就变得单调递增了。`MysQL8.0` 可以更换时间低位和时间高位的存储方式，这样 `UUID` 就是有序的 `UUID` 了
> 2. `MySQL 8.0` 还解决了 `UUID` 存在的空间占用的问题，除去了 `UUID` 字符串中无意义的 `-` 字符串，并且将字符串用**二进制类型**保存，这样存储空间降低为了**16字节**

优点：

1. 适合分布式系统
2. 可以在服务端提前生成
3. 不暴露数据

缺点：

1. 占用空间大
2. 索引大
3. 可读性差
4. 查询日志困难



## `10.3` 雪花 `ID`

雪花 `ID`（`Snowflake ID`）是一种**分布式唯一 ID 生成算法**。它本质上是一个 `64` 位的 `Long` 类型整数，不依赖数据库自增，因此可以由各个应用服务器独立生成。

```sql
0 | 41位时间戳 | 5位数据中心ID | 5位机器ID | 12位序列号

# 如 1938475629384759296
```

> 41 位时间戳：$2^{41} > 2万亿$（13个数数字？），当前时间 - 起始时间，时间戳保证有序
>
> 5位数据中心ID、5位机器ID：$2^5 = 32$，兼容 32 * 32 = 1024 个节点
>
> 12位序列号：$2^{12} = 4096$，因此同一台机器在**同一毫秒**内最多可以生成 4096 个 `ID`

优点：

1. 适合分布式系统
2. 性能高
3. 生成速度快
4. 占用空间小（8 字节）
5. 不暴露数据库数据

缺点：

1. 依赖机器 `ID` 配置
2. 存在时钟回拨问题（改一下服务器的时间试试？）
3. 实现比自增 `ID` 复杂
4. `ID` 比较长，可读性差



| 方案                  | 空间       | 分布式 | 有序性       | 性能   | 主要问题               |
| --------------------- | ---------- | ------ | ------------ | ------ | ---------------------- |
| 自增 `BIGINT`         | **8 字节** | ❌      | **强递增**   | **高** | 依赖数据库             |
| `UUID`                | 16 字节    | ✅      | UUIDv4 无序  | 较高   | 空间大、随机性强       |
| `UUID` + `BINARY(16)` | 16 字节    | ✅      | UUIDv7 较好  | 较高   | 仍比 `BIGINT` 大       |
| **`Snowflake ID`**    | **8 字节** | **✅**  | **趋势递增** | **高** | 时钟回拨、机器 ID 管理 |



## `10.4` 业务字段做主键

1. 卡号 `card_no`
2. 手机号 `phone`
3. 身份证号 `id_card`

业务常常会变化，或者领导一拍脑袋，比如卡号继承、手机号被运营商收回等问题

而更改主键的成本会非常高，所以都不适合做主键

### 核心业务
