# 多版本并发控制

`MVCC`（`Multi-Version Concurrency Control`，多版本并发控制）是数据库领域一个非常核心的概念，尤其在 `MySQL`、`PostgreSQL` 等主流数据库中广泛使用。它的核心思想是：**通过保存数据的多个历史版本，让读操作和写操作互不阻塞，从而大幅提升并发性能**



## `1`. 快照读与当前读

`MVCC` 主要服务于**快照读**，而**当前读**仍然需要加锁

-   **快照读**：普通的 `SELECT`，读取历史版本，不加锁；
-   **当前读**：`SELECT ... FOR UPDATE`、`SELECT ... LOCK IN SHARE MODE`、`UPDATE`、`DELETE`、`INSERT`，读取最新版本并加锁。

**快照读读历史，当前读读最新，并且当前读会加锁**



### `1.2` 快照读

读取的是某个时间点的历史快照版本，而不是最新数据。依靠 `MVCC` 的 `Read View + undo log` 版本链实现，**不加锁**

```sql
SELECT * FROM t WHERE id = 1;
```

普通的 `SELECT` 就是快照读



### `1.3` 当前读

读取的是**最新已提交版本**，并且会**加锁**，保证读到的数据在读取过程中不被其他事务修改

```sql
BEGIN;

SELECT * FROM t WHERE id = 1 FOR UPDATE;          -- 加排他锁
SELECT * FROM t WHERE id = 1 LOCK IN SHARE MODE;  -- 加共享锁
UPDATE t SET name = 'x' WHERE id = 1;             -- 当前读 + 排他锁
DELETE FROM t WHERE id = 1;                       -- 当前读 + 排他锁
INSERT INTO t VALUES (...);                       -- 当前读 + 排他锁

COMMIT;
```





## `2`. `MVCC` 实现原理之 `ReadView`

`MVCC` 的实现依赖于：隐藏字段、`Undo Log`、`ReadView`



### `2.1` 隐藏字段

每行数据除了用户定义的列，`InnoDB` 还会自动加上三个隐藏列

| 字段名        | 占位   | 含义                                             |
| :------------ | :----- | :----------------------------------------------- |
| `DB_TRX_ID`   | 6 字节 | 最近一次插入或修改这行数据的**事务 `ID`**        |
| `DB_ROLL_PTR` | 7 字节 | **回滚指针**，指向 `undo log` 中这行的上一个版本 |
| `DB_ROW_ID`   | 6 字节 | **行标识**，当表没有合适的主键/唯一键时自动生成  |

1.   **隐藏字段是“每行”都有的**

     不是每张表一份，而是每一行数据都带这三个字段。所以 `InnoDB` 表的实际存储比用户看到的列要多出约 19 字节（6+7+6）

2.   **`DELETE` 不是真删除**

     `DELETE` 操作实际上是在当前版本上打一个删除标记（或写入 `delete-mark` 的 `undo` 记录），而不是立刻物理删除。这样快照读才能根据 `ReadView` 判断这行在某个时刻是否存在。真正的物理删除由后台 `purge` 线程完成

3.   **长事务与版本链**

     长事务持有旧 `ReadView`，导致版本链上很多旧版本不能被 `purge` 清理，`undo log` 持续增长。这就是为什么生产环境要尽量避免长事务





#### 隐藏字段与版本链

把 `DB_TRX_ID` 和 `DB_ROLL_PTR` 结合起来，就能看到版本链的形成过程

---

版本链：

1.   事务 100 插入数据

     ```sql
     当前行：id=1, name='Tom', DB_TRX_ID=100, DB_ROLL_PTR=null
     ```

2.   事务 200 把 `name` 改成 `Jerry`

     ```sql
     当前行：id=1, name='Jerry', DB_TRX_ID=200, DB_ROLL_PTR ──┐    # 回滚指针指向 undo log
                                                             ↓
     undo log：  name='Tom', DB_TRX_ID=100, DB_ROLL_PTR=null
     ```

3.   事务 300 把 `name` 再改成 `Spike`

     ```sql
     当前行：id=1, name='Spike', DB_TRX_ID=300, DB_ROLL_PTR ──┐   # 回滚指针指向上一个 undo log
                                                             ↓
     undo log：  name='Jerry', DB_TRX_ID=200, DB_ROLL_PTR ──┐     # 回滚指针指向 undo log
                                                            ↓
     undo log：  name='Tom',   DB_TRX_ID=100, DB_ROLL_PTR=null
     ```

---



### `2.2` `ReadView`

在 `MVCC` 机制中，多个事务对同一个行记录进行更新会产生多个历史快照，这些历史快照保存在 `Undo Log` 里

`ReadView` 可以理解为一个**事务在某个时刻的“可见性判断依据”**。当事务执行快照读时，`InnoDB` 会生成一个 `ReadView`，里面记录了当时数据库中活跃事务的情况。之后读取每一行数据时，就用这个 `ReadView` 去判断某个版本对该事务是否可见

它主要包含四个关键字段：

| 字段             | 含义                                                         |
| :--------------- | :----------------------------------------------------------- |
| `m_ids`          | 生成 `ReadView` 时，当前所有**活跃（未提交）事务**的 `ID` 列表 |
| `min_trx_id`     | `m_ids` 中的最小值，即最小活跃事务 `ID`                      |
| `max_trx_id`     | 生成 `ReadView` 时，系统**下一个将要分配的事务 `ID`**（注意不是 `m_ids` 的最大值） |
| `creator_trx_id` | 创建这个 `ReadView` 的事务自己的 `ID`                        |

这里要特别注意 `max_trx_id`：它是 “下一个待分配” 的 `ID`，所以所有已提交事务的 `ID` 都小于它，而所有未来才开启的事务 `ID` 都大于等于它

>   举个例子，假设当前活跃事务有 `[100, 200]`，下一个待分配 `ID` 是 `300`，本事务 `ID` 是 `150`。
>
>   那么 `ReadView` 为：
>
>   -   `m_ids = [100, 200]`
>   -   `min_trx_id = 100`
>   -   `max_trx_id = 300`
>   -   `creator_trx_id = 150`
>
>   现在读一行数据，版本链最新版本的 `DB_TRX_ID = 200`：
>
>   -   `200` 在 `[100, 300)` 之间，且在 `m_ids` 中 → 未提交，不可见；
>   -   顺着回滚指针找上一版本，假设 `DB_TRX_ID = 90`；
>   -   `90 < 100` → 已提交，可见。
>
>   于是这行数据返回 `90` 那个事务修改后的值



#### `RC` 和 `RR` 的本质区别

这是 `ReadView` 最重要的应用点：

| 隔离级别              | `ReadView` 生成时机                            | 效果                                                         |
| :-------------------- | :--------------------------------------------- | :----------------------------------------------------------- |
| **`READ COMMITTED`**  | **每次快照读**都生成一个新的 `ReadView`        | 每次都能看到最新已提交的数据，所以同一事务多次读结果可能不同 |
| **`REPEATABLE READ`** | **第一次快照读**时生成，之后整个事务复用同一个 | 整个事务看到同一份快照，所以可重复读                         |

>   一句话总结：`ReadView` 是快照读的 “可见性裁判”，通过 `m_ids`、`min_trx_id`、`max_trx_id`、`creator_trx_id` 四个字段，配合版本链逐版本判断，决定当前事务能看到哪个历史版本。`RC` 每次读重建 `ReadView`，`RR` 只建一次并复用，这就是两者最本质的区别
