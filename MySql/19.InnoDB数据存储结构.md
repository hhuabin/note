# `InnoDB` 数据存储结构

`InnoDB` 以“**页（`Page`）**”为基本磁盘存储单位，通过 `B+ 树`组织数据

```
MySQL
│
└── InnoDB 存储引擎
    │
    ├── 表空间（Tablespace）
    │
    ├── 段（Segment）
    │
    ├── 区（Extent）
    │
    ├── 页（Page，默认16KB）⭐
    │
    └── 行（Row / Record）⭐
```

```
# 层级关系
┌─────────────────────┐
│     Tablespace      │
│      表空间          │
│                     │
│   ┌─────────────┐   │
│   │   Segment   │   │
│   │     段       │   │
│   │             │   │
│   │  ┌───────┐  │   │
│   │  │Extent │  │   │
│   │  │  区    │  │   │
│   │  │       │  │   │
│   │  │ Page  │  │   │ ⭐
│   │  │ Page  │  │   │
│   │  │ Page  │  │   │
│   │  └───────┘  │   │
│   └─────────────┘   │
└─────────────────────┘
```



## `1`. 表空间

`MySQL` 现在通常每张表一个 `.ibd` 文件

这个 `.ibd` 文件里不仅仅是表数据，还包含：**数据** + **聚簇索引** + **二级索引**



## `2`. 段

段是 `InnoDB` 中更大的逻辑管理单位。常见的段包括：数据段、索引段、回滚(`Undo`) 段

使用段的原因：

- 问题：对于**范围查询**，其实是对`B+树`叶子节点中的记录进行顺序扫描，而如果不区分叶子节点和非叶子节点，统统把节点代表的页面放到申请到的区中的话，进行范围扫描的效果就大打折扣了。
- 所以 `InnoDB`对 `B+树` 的**叶子节点**和**非叶子节点**进行了区别对待，也就是说叶子节点有自己独有的区，非叶子节点也有自己独有的区。
- 存放叶子节点的区的集合就算是一个段(segment)，存放非叶子节点的区的集合也算是一个段。也就是说**一个索引会生成2个段**。一个**叶子节点段**，一个**非叶子节点段**。
    1. 叶子节点段
    2. 非叶子节点段



## `3`. 区 `Extent`

区可以理解为：一组连续的页

使用过区的原因：

- 相邻的页有助于**范围查找**可以使用顺序IO，加快查询速度；
- 没有区的话，相邻的两个页在磁盘中距离可能非常远，就是所谓的随机 IO，随机 IO 的速度较慢；
- 从性能的角度来说，区可以消除很多的随机 IO；

`InnoDB` 中默认：`1Extent = 64Page`；一个区包含64个页大约1M大小；`1Pgae = 16KB`，`1Extent = 1MB`



## `4`. 页 `Page` :star:

`Page` 是 `InnoDB` 进行磁盘读写的基本单位。默认 `1Pgae = 16KB`

即使只查询一条记录 `SELECT * FROM user WHERE id = 1;`，`InnoDB` 也会从磁盘读取一整个 16KB 的页到内存

```
# Page 内部结构

│ File Header                  │
├──────────────────────────────┤

├──────────────────────────────┤
│ Infimum Record               │

├──────────────────────────────┤

├──────────────────────────────┤
│ File Trailer                 │
└──────────────────────────────┘
```
