## 3.定位执行慢的 `SQL`（慢查询日志）

1.   查看 开启慢查询日志参数

     ```mysql
     SHOW VARIABLES LIKE 'slow_query_log%';         # OFF 关闭。ON 打开
     
     # slow_query_log_file 是日志存放地址
     ```

2.   开启慢查询日志

     ```mysql
     SET GLOBAL slow_query_log = 'ON';                # 生产不要开
     SET GLOBAL slow_query_log = 'OFF';               # 关闭
     ```

3.   查看 慢查询时间 阈值 

     ```mysql
     SHOW VARIABLES LIKE 'long_query_time';          # 默认是 10s，执行时间 > 10s 的 SQL 会被记录
     
     SET GLOBAL long_query_time = 2;                 # 设置阈值为 2s，超过2s就记录，生产不要动
     ```

4.   查看慢查询记录数

     ```mysql
     SHOW STATUS LIKE 'slow_queries';
     ```

5.   慢查询日志分析工具 `mysqldumpslow`（`Linux` 版本）

     ```mysql
     mysqldumpslow -help
     
     mysqldumpslow -s t -t 5 /data/mysql/MySQL-slow.log
     ```

## 5.分析查询语句：`EXPLAIN` :star:

>   `MySQL 8.0`

```mysql
# 基本语法
EXPLAIN SELECT * FROM sys_user;
```

| 字段            | 含义                           | 重点                                     |
| --------------- | ------------------------------ | ---------------------------------------- |
| `id`            | 查询中每个 `SELECT` 的编号     | 判断不同查询块的执行顺序                 |
| `select_type`   | 查询类型                       | `SIMPLE`、`PRIMARY`、`SUBQUERY` 等       |
| `table`         | 当前访问的表                   | 当前正在分析哪张表                       |
| `partitions`    | 使用的分区                     | 表分区时比较重要                         |
| `type`          | **访问类型/连接类型**          | **判断 SQL 是否高效的核心字段**          |
| `possible_keys` | 可能使用的索引                 | MySQL 认为哪些索引可能有用               |
| `key`           | **实际使用的索引**             | **最终选择了哪个索引**                   |
| `key_len`       | 使用索引的长度                 | 判断联合索引实际使用了多少列             |
| `ref`           | 索引与哪个字段进行比较         | 常见于 `=` 条件                          |
| `rows`          | **预计扫描的行数**             | **越小通常越好**                         |
| `filtered`      | 经过条件过滤后剩余数据的百分比 | 与 `rows` 一起判断扫描效率               |
| `Extra`         | 额外执行信息                   | **非常重要，常能发现排序、临时表等问题** |

-   实际执行情况

    | 命令              | 作用                                   |
    | ----------------- | -------------------------------------- |
    | `EXPLAIN`         | 查看 `MySQL` **预计怎么执行**          |
    | `EXPLAIN ANALYZE` | **实际执行** `SQL`，并返回实际执行情况 |

    ```mysql
    # EXPLAIN 只是列出 SQL 的预计的执行计划，不会真的删除数据
    EXPLAIN
    DELETE FROM sys_user
    WHERE id = 1;
    
    # EXPLAIN ANALYZE 会实际执行 SQL，所以 id = 1 的记录会被删除
    EXPLAIN ANALYZE
    DELETE FROM sys_user
    WHERE id = 1;
    ```




### 5.1 `id`：查询编号

简单查询通常就是：`id = 1`

如果存在子查询、`UNION` 等，可能出现多个 `id`

```mysql
id
1
2
```

1.   `id` 如果相同，可以认为是一组，从上往下顺序执行
2.   在所有组中，`id` 值越大，优先级越高，越先执行
3.   关注点：`id` 号每个号码，表示一趟独立的查询，一个 `sql` 的查询趟数越少越好



### 5.2 `select_type` 查询类型

| 值             | 含义           |
| -------------- | -------------- |
| `SIMPLE`       | 简单查询       |
| `PRIMARY`      | 最外层查询     |
| `SUBQUERY`     | 子查询         |
| `DERIVED`      | 派生表         |
| `UNION`        | `UNION` 查询   |
| `UNION RESULT` | `UNION` 的结果 |



### 5.3 `table` 表

当前正在访问的表，如 `table = employees` 说明当前执行计划针对 `employees` 这张表



### 5.4 `partitions` 使用的分区

看这条 `SQL` 实际需要访问哪些表分区；普通非分区表一般显示 `NULL`

>   **数据库分区**：分区（Partition）就是把一张表的数据按照某种规则，拆分到多个分区中进行存储
>
>   **分区：一张表拆成多个“物理分区”，但在逻辑上还是一张表。**
>   **分表：一张逻辑表拆成多张独立的表。**
>   **分库：一个数据库拆到多个数据库实例/库中。**
>
>   ```mysql
>   CREATE TABLE orders (
>       id BIGINT,
>       user_id BIGINT,
>       amount DECIMAL(10,2),
>       create_time DATETIME
>   )
>   PARTITION BY RANGE (YEAR(create_time)) (
>       PARTITION p2024 VALUES LESS THAN (2025),
>       PARTITION p2025 VALUES LESS THAN (2026),
>       PARTITION p2026 VALUES LESS THAN (2027),
>       PARTITION pmax VALUES LESS THAN MAXVALUE
>   );
>   ```
>
>   | 分区类型 | 分区依据         | 常见用途           |
>   | -------- | ---------------- | ------------------ |
>   | `RANGE`  | 范围             | 按年份、月份、日期 |
>   | `LIST`   | 指定值列表       | 按地区、类别等     |
>   | `HASH`   | 哈希结果         | 尽量均匀分散数据   |
>   | `KEY`    | MySQL 计算的哈希 | 类似 HASH          |



### 5.5 `type` 访问类型 :star:

`MySQL` 访问表中数据时采用什么方式

| `type`            | 含义                                                  | 典型场景                                       | `SQL` 示例                                                   |
| ----------------- | ----------------------------------------------------- | ---------------------------------------------- | ------------------------------------------------------------ |
| `system`          | 表只有 **1 行数据**                                   | 系统表、只有一条记录的表                       | `SELECT * FROM config;`                                      |
| **`const`**       | 通过**主键/唯一索引等值查询**，最多返回 1 行          | 单表根据主键查询                               | `SELECT * FROM user WHERE id = 1;`                           |
| `eq_ref`          | `JOIN` 时通过**主键/唯一索引等值匹配**，每次最多 1 行 | 主表 JOIN 从表的主键/唯一键                    | `SELECT * FROM orders o JOIN user u ON o.user_id = u.id;`    |
| **`ref`**         | 通过**普通索引等值查询**，可能返回多行                | `=` 查询普通索引列                             | `SELECT * FROM user WHERE dept_id = 10;`                     |
| `fulltext`        | 使用**全文索引**                                      | `MATCH ... AGAINST` 全文搜索                   | `SELECT * FROM article WHERE MATCH(content) AGAINST('MySQL');` |
| `ref_or_null`     | `ref` + `IS NULL`                                     | 索引列既查询某个值，又查询 `NULL`              | `WHERE dept_id = 10 OR dept_id IS NULL`                      |
| `index_merge`     | **多个索引合并**使用                                  | `OR`、多个条件分别命中不同索引                 | `WHERE name = '张三' OR age = 20`                            |
| `unique_subquery` | 子查询使用**唯一索引**                                | `IN` 子查询 + 主键/唯一索引                    | `WHERE user_id IN (SELECT id FROM user ...)`                 |
| `index_subquery`  | 子查询使用**普通索引**                                | `IN` 子查询 + 普通索引                         | `WHERE dept_id IN (SELECT dept_id FROM dept_user ...)`       |
| **`range`**       | **索引范围扫描**                                      | `> < >= <= BETWEEN IN` 等                      | `WHERE age BETWEEN 18 AND 30`                                |
| `index`           | **全索引扫描**                                        | 查询可以直接从索引得到数据，但需要扫描整个索引 | `SELECT id FROM user;`                                       |
| `ALL`             | **全表扫描**                                          | 没有合适索引，扫描整张表                       | `SELECT * FROM user WHERE name LIKE '%张%';`                 |

>   对于该表，一般越靠上越好，越靠下需要越关注性能
>
>   `SQL` 性能优化目标：要求是 `ref` 级别，最好是 `const` 级别，最差是 `range` 级别



### 5.6 `possible_keys`

`MySQL` 认为**可能**可以使用哪些索引，如： `PRIMARY,emp_emp_id_pk`



### 5.7 `key` :star:

`MySQL` 最终**实际**选择使用的索引，如：`PRIMARY`



### 5.8 `key_len`

实际使用的**索引长度**（字节长度），如 4，说明使用了 4 字节。没有使用索引返回 `NULL`

这个字段对于分析**联合索引**非常有用



### 5.9 `ref`

`ref`：当使用索引列等值查询时，与索引列进行等值匹配的对象信息。比如只是一个常数或者是某个列。

例如：`WHERE department_id = 10`，可能看到：`xxxxxxxxxx ref = const`

如果是表连接：

```
SELECT *
FROM employees e
JOIN department d
ON e.department_id = d.id;
```

可能出现类似：

```
ref = d.id
```



### 5.10 `rows` :star:

`MySQL` 预计需要检查多少行，值越小越好

```mysql
EXPLAIN
SELECT *
FROM sys_user
WHERE id = 100;
```

一般 `rows` 返回 1，

```mysql
SELECT *
FROM sys_user;
```

一般 `rows` 返回 表的全部记录数



### 5.11 `filtered`

`MySQL` 预计经过当前条件过滤后，剩余数据占扫描数据的百分比，它主要用于辅助判断过滤效率

>   $rows*\frac{filtered}{100}$ 值越小说明需要进一步处理的行数更少

```mysql
rows = 1000
filtered = 10
```

可以粗略理解为：预计检查 1000 行，大约 10% 符合条件，约 1000 * 10% =  100 行，需要处理 100 条数据‘

>   `filtered` 并不精准，只是大概准确，所以不用太纠结精准度



### 5.12 `Extra` :star:

`MySQL` 在执行过程中进行了哪些额外操作

| `Extra`                     | 含义                      | 典型场景                                  |
| --------------------------- | ------------------------- | ----------------------------------------- |
| **`Using where`**           | 使用 `WHERE` 条件过滤     | `WHERE age > 18`                          |
| **`Using index`**           | 使用覆盖索引，无需回表    | `SELECT id FROM user WHERE id = 1`        |
| **`Using index condition`** | 使用索引条件下推（ICP）   | 联合索引查询时进一步过滤                  |
| **`Using temporary`**       | 使用临时表                | `GROUP BY`、`DISTINCT` 等                 |
| **`Using filesort`**        | 需要额外排序              | `ORDER BY` 无法利用索引                   |
| **`Using join buffer`**     | `JOIN` 使用 `Join Buffer` | `JOIN` 条件没有合适索引，可能需要建立索引 |
| `Using index for group-by`  | 使用索引完成分组          | `GROUP BY` 字段有合适索引                 |
| `Using MRR`                 | 使用多范围读取优化        | 二级索引范围查询、回表                    |
| `Impossible WHERE`          | `WHERE` 条件不可能成立    | `WHERE 1 = 0`                             |
| `Using intersect(...)`      | 多个索引结果取交集        | `index_merge` + `AND`                     |
| `Using union(...)`          | 多个索引结果取并集        | `index_merge` + `OR`                      |
| `NULL`                      | 没有额外信息              | 普通查询                                  |





## 6. `EXPLAIN` 的 `FORMAT`

| FORMAT        | 说明        | 特点                                |
| ------------- | ----------- | ----------------------------------- |
| `TRADITIONAL` | 默认格式    | 传统表格形式，和普通 `EXPLAIN` 一样 |
| **`JSON`**    | `JSON` 格式 | 信息更详细，适合分析执行计划        |
| `TREE`        | 树形格式    | 用树形结构展示执行过程，可读性较好  |

```mysql
EXPLAIN FORMAT = JSON
SELECT *
FROM employees;
```

## 8. `trace`

| 工具              | 主要回答的问题                   |
| ----------------- | -------------------------------- |
| `EXPLAIN`         | 最终怎么执行？                   |
| `EXPLAIN ANALYZE` | 实际是怎么执行的？实际耗时多少？ |
| `optimizer_trace` | 优化器为什么这么选择？           |

平时优化 `SQL`，通常优先使用 `EXPLAIN`

如果还不明白，为什么 `MySQL` 不使用我创建的索引 或者 为什么优化器选择了这个执行计划，这时候再使用`optimizer_trace`

```mysql
# 使用 optimizer_trace
SELECT @@session.optimizer_trace;
SELECT @@session.end_markers_in_json;

# trace 默认是关闭的状态，先开启
SET SESSION optimizer_trace = 'enabled=on';
SET SESSION end_markers_in_json = 1;                        # 设置格式为 json，可以不设置

# 执行别的 sql 语句之后再执行即可看到结果
SELECT * FROM information_schema.OPTIMIZER_TRACE;
SELECT * FROM information_schema.OPTIMIZER_TRACE\G;         # 控制台使用
```



## 9. `MySQL` 监控分析视图-`sys schema`

>   默认数据库：`sys`

```mysql
# 查看常用的 sys schema
SHOW TABLES FROM sys;
```

| sys 常用视图                          | 主要用途                     |
| ------------------------------------- | ---------------------------- |
| `statement_analysis`                  | `SQL` 执行情况分析           |
| `schema_table_statistics`             | 表的访问统计                 |
| `schema_index_statistics`             | 索引使用统计                 |
| `schema_unused_indexes`               | 查找可能没使用的索引         |
| `processlist`                         | 查看当前正在执行的线程/`SQL` |
| `io_global_by_file_by_bytes`          | `IO` 情况分析                |
| `memory_global_by_current_bytes`      | 内存使用情况                 |
| `schema_tables_with_full_table_scans` | 查找全表扫描较多的表         |

```mysql
# 查询索引的使用情况
SELECT *
FROM sys.schema_index_statistics;

# 查询表的访问量
SELECT *
FROM sys.schema_table_statistics;

# 查询 SQL  执行情况分析（statement_analysis 表）
SELECT db, exec_count, tmp_tables, tmp_disk_tables, `query`
FROM sys.statement_analysis
WHERE tmp_tables > 0 OR tmp_disk_tables > 0
ORDER BY (tmp_tables + tmp_disk_tables) DESC;
```
